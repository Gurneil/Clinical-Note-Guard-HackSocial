# The prompts, and what every constraint in them is doing

This is the prompt-engineering record for the pipeline. `ARCHITECTURE.md`
explains why the *workflow* is shaped the way it is; this file is about the
text sent to the models, the specific constraints engineered into it, and
what those constraints were each written in response to.

The authoritative version of every prompt is `src/pipeline.py` (and
`src/baseline.py` for the comparison baseline). The prompts below are
reproduced from there; `{braces}` are Python f-string interpolations.

## The rules that apply to every prompt

Five constraints show up in nearly every node, because each one closes a
failure mode that actually occurred during development:

| Constraint | What it prevents |
|---|---|
| `Return ONLY a JSON array... No markdown` | Models wrapping JSON in ```` ```json ```` fences, or prefacing it with "Sure! Here's the analysis:". The client strips fences defensively as well (`src/openai_compat_client.py`), because instruction alone was not reliable across providers. |
| `EXACTLY {n} objects... do not skip or merge any` | Batched calls silently returning fewer results than items sent. See "Batching without losing the per-item guarantee" below. |
| `in the SAME ORDER as listed above` + numbered inputs | Results that can't be mapped back to their input. Position is the join key, so order is load-bearing, not cosmetic. |
| `Check EVERY claim independently - your judgment on one claim must not influence any other` | The model reading the note as a narrative and deciding it "seems fine overall", which is exactly the single-pass failure the whole pipeline exists to avoid. |
| `decide exactly ONE status: "supported" \| "contradicted" \| "not_mentioned"` | Free-text verdicts that can't be counted, compared, or scored. A closed label set is what makes the output auditable. |

A sixth rule is enforced in code rather than in the prompt: **a count
mismatch raises**, it is never silently accepted.

```python
if not isinstance(result, list) or len(result) != len(claims):
    got = len(result) if isinstance(result, list) else type(result).__name__
    raise ValueError(...)
```

If the model returns 11 verdicts for 12 claims, the run fails loudly. The
alternative - zipping them up and moving on - would mean one claim silently
inherits another claim's verdict, and the system would report a confident
answer about a claim it never actually checked. In a documentation-QA tool
that is the worst possible failure, because it is invisible.

## Node 1 - draft the note

Simulates the ambient scribe whose output everything downstream checks.
Not a QA prompt; deliberately unremarkable, because a hardened drafting
prompt would make the benchmark easier than reality.

```
You are an ambient clinical scribe. Read the following
doctor-patient conversation transcript and produce a structured SOAP note
(Subjective, Objective, Assessment, Plan). Only include information that
was actually discussed in the transcript.

TRANSCRIPT:
{transcript}

Return only the SOAP note, no preamble.
```

Note that this prompt already says "only include information that was
actually discussed" - and hallucinations still occur downstream of it,
which is the premise of the entire project. Instructing a model not to
fabricate is not a control; verifying that it didn't is.

## Node 2 - extract atomic claims

```
Break the following clinical note into a list of atomic,
independently-checkable factual claims. Each claim should be one discrete
fact (one symptom, one medication + dose, one vital sign, one plan item,
etc). Do not combine multiple facts into one claim.

Do NOT include the clinician's overall diagnosis or clinical impression
as a claim - this applies regardless of which section it appears in or
how it's phrased (an "Assessment:" line, a sentence describing what
condition is suspected or confirmed, etc). A diagnosis is the
clinician's synthesized judgment, not something directly stated by the
patient [...] Directly-reportable facts the diagnosis is BASED on
(symptoms, exam findings, test results) should still be included as
their own separate claims.

NOTE:
{note}

Return ONLY a JSON array of strings [...]
```

**The diagnosis exclusion is the whole point of this prompt.** Without it,
every note's `Assessment:` line became a claim, and node 3 then checked
"Hypertension, well-controlled" against a transcript where nobody says the
word "hypertension" - and correctly reported it as unsupported. That is a
false positive generated by the pipeline's own design, not a documentation
error: a diagnosis is a clinician's synthesis, so literal transcript
grounding is the wrong test for it.

Note what the exclusion does *not* do: the findings a diagnosis rests on
(the BP reading, the symptom, the lab value) stay in as separate claims.
The judgment is exempt; the facts under it are not.

## Node 3 - entailment check (batched)

The core reasoning step, and the only one fairness-linked to the baseline.

```
You are checking whether each of the following claims from a clinical
note is supported by a source transcript. Check EVERY claim
independently - your judgment on one claim must not influence any other.

A claim is "supported" if the transcript conveys the same meaning, even
in different words - do not require an exact wording match. In
particular:
- Clinical terminology in the note that restates a lay description in
  the transcript counts as supported (e.g. transcript "red and swollen"
  supports note "erythematous and enlarged"; transcript "white patches"
  supports note "exudate").
- A note statement that summarizes or combines multiple things the
  transcript said is supported if everything in it was actually said [...]
Only mark "contradicted" if the note states something that conflicts
with the transcript, and only mark "not_mentioned" if the transcript
truly gives no indication of it at all, directly or through a synonym.

TRANSCRIPT:
{transcript}

CLAIMS TO CHECK ({len(claims)} total, check each independently):
{numbered}

For EACH claim, decide exactly ONE status [...]
Return ONLY a JSON array with EXACTLY {len(claims)} objects, one per
claim, in the SAME ORDER as listed above:
[{"claim_number": 1, "status": "...", "evidence": "exact quote from the
transcript, or empty string if not_mentioned"}, ...]
```

Three deliberate choices:

**The paraphrase allowance was added mid-eval, in response to real false
positives.** The first version required the transcript to support the
claim without saying how, and the model read that as near-literal
matching: a note saying "erythematous" against a transcript saying "red
and swollen" came back *contradicted*. The two worked examples are in the
prompt because abstract instructions ("allow synonyms") did not move the
behaviour; concrete pairs did.

**`evidence` is mandatory and must be a quote.** Requiring the model to
produce the supporting span does double duty: it is what the reviewer
reads in the UI, and it makes an unsupported "supported" verdict harder to
produce, because the model has to point at something.

**"Contradicted" and "not_mentioned" are kept separate** rather than
collapsed into "unsupported". They are clinically different - a wrong dose
is not the same event as a detail the transcript never covered - and node
6 needs the distinction to classify correctly.

## Node 4 - deterministic numeric check

No prompt. This node is a regex, deliberately: an exact number either
appears in the transcript or it does not, and that question does not need
a model's judgment. See `ARCHITECTURE.md` ("Does each node earn its
place?") for the ablation showing what this node did and did not
contribute.

## Node 5 - omission check (batched)

The mirror image of nodes 2+3: facts are extracted from the *transcript*,
then checked against the note.

```
You are checking whether each of the following facts from a
doctor-patient transcript was included (even if paraphrased or
summarized) in a clinical note written from that transcript. Check EVERY
fact independently.

A fact counts as "mentioned" if it is covered in ANY of these ways:
- stated directly, in the same or different words
- covered by a broader summarizing statement in the note (e.g. a note
  saying "denies changes in weight, appetite, sleep, or energy" mentions
  each of those four facts individually, even though none is its own
  sentence)
- referred to using a reasonable clinical synonym (e.g. "lipid panel"
  and "cholesterol panel" refer to the same test; "sulfa allergy" and
  "allergic to sulfa drugs" are the same fact)
Only mark a fact "omitted" if the note truly gives no indication of it
at all [...]
```

**The "broader summarizing statement" rule exists because of a specific
measured failure.** On `case_18` (a genuinely clean note), the pipeline
raised 7 flags, 4 of which were the note's single line "denies changes in
weight, appetite, sleep, or energy" being scored against four separately
extracted transcript facts. The summarizing rule - with that exact
sentence as the worked example - was written to close it.

**It did not fully close it, and `ARCHITECTURE.md` says so.** A residual
case survives: when the transcript says something like "everything's been
stable" and the note enumerates the four specific negations, recognising
that a general statement implies several specific ones is a harder
inference than synonym matching. This was deliberately *not* chased with
more prompt patches - each fix so far targeted a clear, generalizable gap,
and past that point narrow patches start fitting the prompt to the
benchmark rather than to the problem.

## Node 6 - classify each flag

```
Classify each of the following flagged claims into exactly ONE category
from this list:

{categories}          <- injected from taxonomy.json, not hardcoded here

FLAGGED CLAIMS ({len(flagged)} total):
{numbered}

Return ONLY a JSON array with EXACTLY {len(flagged)} objects, in the SAME
ORDER as listed above:
[{"item_number": 1, "category": "<one of the ids above>",
  "explanation": "one sentence"}, ...]
```

The category list is injected from `taxonomy.json` rather than written
into the prompt, so the taxonomy has exactly one definition in the repo.
The model picks from a closed set of ids; it cannot invent a category,
which is what keeps flags comparable across cases and scoreable at all.

## The baseline prompt, and why it was strengthened

The comparison baseline is the naive version of this product: one call,
transcript plus note, "find the errors."

```
You are given a doctor-patient conversation transcript and a clinical
note that was generated from it. Carefully review the note against the
transcript and identify any documentation errors.

Look for BOTH kinds of error:
1. Anything stated in the note that the transcript does not support -
   fabricated details, wrong numbers or doses, altered severity, a
   denial reported as an affirmation (or vice versa), or something
   attributed to the wrong person.
2. Anything clinically relevant that the transcript states but the note
   leaves out entirely.
```

**Point 2 was added deliberately, and it made the baseline harder to
beat.** The original baseline prompt only asked about unsupported
content. The pipeline has a dedicated omission node, so any omission the
baseline missed would have been scored as a pipeline win - a win produced
by the prompt being unfair rather than by the workflow being better.
Telling the baseline explicitly to look for both error types removes that
artifact. The pipeline's measured recall advantage survived the change,
which is the only reason it is reported as evidence.

This is the one prompt-engineering decision in the project that was made
*against* the project's own headline number, and it is the reason the
comparison is worth anything.

## Batching without losing the per-item guarantee

Nodes 3 and 5 originally issued one API call per claim. That was clean but
unusable in practice: a 14-claim note meant 14 sequential calls, and free
tier rate limits made a 60-case eval impossible.

Batching all claims into one call reintroduces the exact risk the pipeline
was built to eliminate - a model glancing over a list and returning a
holistic impression. Three constraints hold the per-item guarantee open
across the batch:

1. Inputs are **numbered**, and outputs must carry the number back
   (`claim_number`, `fact_number`, `item_number`).
2. The output count is stated twice - once in the schema line, once as a
   closing imperative (`You MUST return exactly {n} objects`). Repetition
   at the end of a long prompt measurably helped; models drift on
   instructions buried above a long transcript.
3. The count is **verified in code**, and a mismatch raises.

Constraint 3 is the one that actually guarantees anything. The first two
make compliance likely; only the check makes a violation impossible to
miss.

## What is deliberately *not* in these prompts

- **No few-shot examples of planted errors.** Showing the model the kinds
  of error the benchmark contains would inflate recall on this benchmark
  specifically, and would not generalize to error types nobody planted.
  The worked examples that *are* present are all paraphrase-recognition
  examples - they teach the model when *not* to flag, which biases against
  the project's own headline metric rather than toward it.
- **No "you are an expert clinician" framing.** The model is not being
  asked for clinical judgment at any point. Every prompt asks a textual
  question: is this claim in that transcript. Role-priming it as a
  clinician invites exactly the judgment this system is designed not to
  make.
- **No confidence scores.** A model-reported confidence would look
  informative and would be unvalidated. Every flag goes to a human either
  way, so the honest interface is the evidence quote, not a number.
